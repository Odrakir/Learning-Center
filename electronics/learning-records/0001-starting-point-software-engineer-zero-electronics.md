# Starting point: strong software engineer, zero electronics

Established at course creation (2026-08-27), before any lesson. Ricardo is a
practising software engineer but has no electronics background at all — no
components, no multimeter, no soldering iron, and no exposure to the
fundamentals. He explicitly chose real foundations over the fastest path to a
working robot, and chose to stay screen-only until the basics prove they'll
stick.

## Implications

- **Do not teach programming.** Code, abstraction, logic, debugging and
  spec-reading are all available to draw on. When Arduino code appears, explain
  the *electrical* meaning of each line, never the C++ syntax. Analogies to
  software systems (throughput vs. pressure vs. bottleneck; datasheets as API
  docs) are a genuine shortcut here and should be used.
- **Do teach the physics from zero**, with no assumed intuition. The gap is
  entirely in what electricity actually *is*, not in how to think rigorously.
- **Every lesson needs an in-browser feedback loop.** There is no breadboard to
  fall back on, so simulation is not a supplement — it is the only lab bench
  until he buys hardware. Falstad/CircuitJS carries this; Tinkercad Circuits
  takes over once a microcontroller is in play.
- **Sets the pace floor for depth, not for speed.** Choosing "understand it
  properly" means theory that explains a robot need is in scope, and black-boxed
  modules are not. Re-check this if he starts sounding impatient for the build.

This is a prior-knowledge record, not evidence of learning — nothing has been
demonstrated yet. The first real learning record should come from evidence in
Lesson 1's drill, not from the lesson having been delivered.
